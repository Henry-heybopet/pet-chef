## 第一阶段控制策略

第一阶段先不接入 Tuya 云菜谱和多步骤菜谱系统，优先使用 `diy` 模式跑通 App 到机器的最小控制闭环：

```json
{
  "1": true,
  "3": "diy",
  "7": 1200,
  "9": 85,
  "102": 8,
  "108": "1",
  "107": "start"
}
```

含义：

- `1 power`: 打开设备。
- `3 mode`: 使用 `diy` 模式。
- `7 cook_time`: 计划烹饪时间，单位秒。
- `9 cook_temperature`: 烹饪温度，第一版默认 85 摄氏度。
- `102 cook_mode_power`: 功率档位，第一版默认 8。
- `108 cook_mode_speed`: 搅拌速度，第一版默认 `1`。
- `107 cook_s_p_r`: 启动/暂停/复位，启动时下发 `start`。

## 状态枚举

`status`:

- `standby`: 待机中
- `appointment`: 预约中
- `cooking`: 烹饪中
- `done`: 烹饪完成
- `pause`: 烹饪暂停
- `Add_Ingredients`: 加料中

`cook_s_p_r`:

- `start`: 启动
- `pause`: 暂停
- `reset`: 复位

## 和工厂联调时必须确认

1. 多个 DP 是否可以一次性下发，还是必须按顺序分批下发。
2. `cook_s_p_r=start` 是否必须最后下发。
3. MCU 收到 `DP7 cook_time` 后是否会按该秒数原生停止；若仍向上计时，需要工厂检查 MCU 对 DP7 的实现。
4. `cook_temperature=85` 实机是否可以稳定低温控制。
5. `cook_mode_speed` 的 `L` 与 `1-10` 分别对应什么转速。
6. `cook_mode_power=8` 的实际加热功率范围。
7. `fault` 的 `E01/E02/E03/E04/E05/E07/E08/E11` 具体故障含义。
8. 设备配网方式：EZ、AP、蓝牙辅助、扫码中支持哪些。
9. 设备复位/进入配网模式的按键方式。

## 低温烹饪流程

- 用户在待机页首次点击“启动一键烹饪”时先下发 `DP107=reset`，随后打开安全确认弹窗；用户在弹窗确认后才下发目标温度、功率、转速和 `DP7` 计划总秒数，并单独下发 `DP107=start`。参数和启动命令禁止放在同一个无序 Map 中，避免 MCU 先执行启动再接收时长。
- 烹饪总时长不再包含预加热：100 克读取食谱数据库 `cooking_profile.cook_minutes`，缺失时为 10 分钟；200/300/400/500/600/700/800 克依次为 15/18/21/25/29/34/39 分钟。
- App 只提供 1–8 份选择，每份固定 100 克；后端仅接受 100、200、300、400、500、600、700、800 克，其他克重拒绝启动。
- `DP5 status` 是 App 烹饪状态的唯一来源：`standby` 显示“启动一键烹饪”，`cooking` 显示“低温烹饪中”，`pause` 显示“烹饪暂停中”，`done` 显示可点击的“烹饪完成”。App 不根据 DP107、手机计时器、本地缓存或后端 DP 缓存推断/合成状态；每次订阅后都要由原生 Tuya SDK 拉取一次家庭设备快照。设备列表返回的 DP 只用于设备发现，不写入状态缓存；订阅快照只在尚未收到实时 `dpUpdate` 时使用。实时回调先到时，延迟返回的快照必须丢弃，不能覆盖较新的 DP5。在线设备尚未取得原生 DP5 时显示“同步设备状态中”，而不是猜测待机。
- `DP8 remain_time` 是 App 倒计时的唯一校准来源。每次原生 Tuya SDK 上报 DP8 后立即校准；DP5 为 `cooking` 时，App 在两次上报之间按本机经过时间逐秒刷新显示，下一次 DP8 到达时重新对齐。DP5 为 `pause` 时冻结在最新 DP8，DP5 为 `done` 时显示零；本地显示不得自行切换状态、判定完成或发送设备命令。缺少 DP8 时显示 `--:--`。
- App 仅允许用户下发一次“启动一键烹饪”。启动后，暂停、恢复和停止只能在鲜食机实体按键操作；App 不再提供或自动下发 `DP107=pause`、`reset` 或 `start` 控制。开始新一轮烹饪时，仅按“首次点击 reset → 确认后参数 → start”执行；烹饪完成时用户点击“烹饪完成”后下发 `DP107=reset`，仍等待 DP5 回报 `standby`。
- `DP12=fault=2`（鲜食杯未安装）会在 App 显示故障并阻止待机状态下启动；运行中由鲜食机固件自行执行安全保护，App 不额外发送暂停命令。
- SDK 命令发送成功只表示指令已交给 Tuya SDK，不代表鲜食机已执行。App 发送启动后仍等待设备 DP5 变为 `cooking`；在此之前不会伪造“启动中”或“烹饪中”状态。
- 正常情况下 MCU 应根据 DP7 原生计时并停止。运行任务必须按 `devId` 持久化食谱、宠物、克重及烹饪参数；用户从任何页面返回烹饪页时，只要设备仍为 `cooking`、`pause` 或 `done`，都优先展示该运行任务，不能被路由中下一份待烹饪食谱覆盖。App 被系统杀死时的硬件侧精确停止仍必须依赖 MCU 正确实现 DP7。
- “零食自制”使用相同启动链路：温度限制 `40–120°C`，转速限制 `1–10` 档，时长限制 `1–43920` 秒，功率固定为 `DP102=8`。点击“启动一键烹饪”后立即进入设备烹饪前页面，完整鲜食安全检查和能量估算在后台并行执行；用户确认启动时必须等待检查完成，危险食材、检查失败或能量不可用均禁止下发设备命令。检查通过后再下发 DP9、DP7、DP102、DP108 和 DP107。
- 多设备账号从食谱“一键烹饪”进入时必须先明确选择一台在线设备，不得默认向设备列表第一台发送命令；单设备账号可直接进入该设备控制页。
- 用户修改鲜食机名称时同时更新 Tuya 设备名称和 Heybo 后端设备缓存；设备唯一标识仍使用 `devId`，名称只用于展示，不参与命令路由。
## 状态一致性原则

运行中的食谱名称、宠物和份量只作为展示上下文按 `devId` 缓存；设备状态和剩余时间不从该缓存恢复。当前会话收到 SDK 原生 DP 增量包后只在 UI 内合并全部 DP：DP5 仅用于状态，DP8 仅用于倒计时，不能因该包不含 DP5 而丢弃 DP8。同步到 Heybo 后端时必须提交 SDK 的原始增量包，不能上传合并缓存，否则后续 DP8 可能把旧 DP5 重放为新的状态。Heybo 后端 DP 仅用于设备通讯日志、历史和离线缓存，不参与在线状态判定；页面重新进入后通过 SDK 家庭设备快照校正 DP5/DP8。

## 设备通讯日志

- Admin 设备弹窗将“设备操作日志”和“设备通讯日志”分开显示。
- App→设备在 Tuya SDK 命令发送成功后记录每个控制 DP；设备→App 记录 DP5 状态变化、每次变化的 DP8 倒计时和 DP12 故障变化。
- DP8 日志保存 SDK 回调中的原始增量值，用于核对设备是否每秒上报以及 APP 是否持续收到；不得用 UI 本地插值值写日志，也不得把 UI 合并缓存作为新设备上报。
- 高频通讯日志在服务端滚动保留最新 2000 条，Admin 读取最新 1000 条，避免 DP8 每秒上报导致 JSON 存储无限增长，同时保留一次完整调测所需的启动、运行与结束时序。
- 每台设备的 App→设备与设备→App 日志请求使用同一条前端异步队列，保证后台写入顺序；日志网络请求不得被 `await` 在 Reset/Start 设备指令之前。
